# `git-ots` Specification

## 1. Purpose

`git-ots` is a small command-line tool that periodically anchors Git repository states using OpenTimestamps.

The tool is designed around three independently configurable timestamping policies:

1. **Every commit** — timestamp every meaningful Git commit.
2. **Maximum age** — ensure meaningful changes do not remain unstamped longer than a configured duration.
3. **Fixed time of day** — timestamp the latest meaningful repository state at a configured wall-clock time.

The policies may be enabled independently or combined.

For the maximum-age and fixed-time policies, a timestamp is created **only if meaningful changes exist** since the last timestamped repository state.

OpenTimestamps proof files are stored in the repository and committed. Commits generated solely to store or update proofs are considered generated metadata and must never themselves cause another timestamp.

The tool must be safe to invoke repeatedly. If no policy requires action, repeated invocations must have no externally visible effect.

---

## 2. Design goals

The implementation SHALL provide the following properties.

### 2.1 Meaningful changes are eventually timestamped

If the maximum-age policy is enabled, a meaningful commit SHALL not remain unstamped beyond the configured maximum age, subject to scheduler latency.

For example, with:

```text
git config ots.maxAge 24h
```

a meaningful commit should normally be included in an OpenTimestamps submission within 24 hours of its Git committer timestamp.

The actual upper bound is:

```text
configured max_age + scheduler invocation latency
```

The CLI itself is not a daemon and therefore cannot guarantee execution at an exact instant unless invoked by an external scheduler.

### 2.2 Multiple commits may collapse into one timestamp

When `every_commit` is disabled, multiple meaningful commits that accumulate before a policy trigger SHALL be represented by a single timestamp of the newest meaningful state.

Example:

```text
00:00  timestamp A

01:00  commit B
06:00  commit C
18:00  commit D

00:00  timestamp D
```

B and C require no separate timestamp because timestamping D cryptographically identifies the repository state containing them.

### 2.3 Proof bookkeeping must not trigger timestamps

A proof commit created by `git-ots` SHALL not count as a meaningful repository change.

Example:

```text
source commit D
    ↓
timestamp D
    ↓
write proof for D
    ↓
commit proof
```

Immediately invoking `git-ots` again SHALL produce no new timestamp.

### 2.4 The default source ref is `HEAD`

The default source state SHALL be the current branch tip.

```text
git config ots.sourceRef HEAD
```

This makes stamping before publication a first-class use case; a Git commit
hash is identical whether the commit is local or on a forge, so the remote is
not a cryptographic trust boundary.

Users who prefer to timestamp only pushed state MAY configure the upstream ref:

```text
git config ots.sourceRef '@{upstream}'
```

That upstream-only mode is a churn-and-cost preference, not a safety property.


### 2.5 Timestamped states are permanently identifiable

Every successfully submitted source commit SHALL receive an immutable annotated Git tag.

The tag points to the **source commit whose identifier was timestamped**, not to the subsequent generated proof commit.

# 3. Terminology

## 3.1 Source commit

A Git commit representing repository content that may require timestamping.

## 3.2 Meaningful commit

A commit that is not an `git-ots`-generated proof commit.

Normal user changes to proof files are still meaningful unless the commit itself carries valid `git-ots` generated-commit metadata.

## 3.3 Proof commit

A commit generated by `git-ots` whose sole purpose is to store or update OpenTimestamps proof material and associated metadata.

## 3.4 Timestamped source commit

A source commit for which OpenTimestamps submission completed successfully and an `git-ots` timestamp tag was created.

## 3.5 Pending commit

A meaningful source commit newer than the most recent relevant timestamped source state.

## 3.6 Latest pending commit

The newest pending meaningful commit reachable from the configured source ref.

## 3.7 Oldest pending commit

The oldest pending meaningful commit reachable from the configured source ref.

It determines whether the maximum-age rule has become due.

# 5. Configuration

Configuration SHALL live in Git config, under the `ots.*` namespace. There is
no configuration file of the tool's own: `git config` is the format, the
storage and the precedence mechanism.

```text
git config ots.maxAge 24h
```

This is deliberate: configuration that a clone can carry is configuration an
attacker can supply. Git config is
never carried by a clone, so a fetched repository cannot influence what this
tool does. See §28.7.

Keys SHALL be read from every Git config scope — `system`, `global`, `local`,
`worktree` — and, being ordinary Git config, respond to `git -c` and the
`GIT_CONFIG_*` environment variables without the tool implementing an override
mechanism of its own.

Git lower-cases configuration key names, so `ots.maxAge` and `ots.maxage` name
the same key; the camel-case spelling is used throughout this document for
readability. Keys under `ots.*` that this table does not name SHALL be rejected
with the invalid-configuration exit code, naming both the offending key and the
namespace.

| Key | Type | Default | Meaning |
|---|---|---|---|
| `ots.everyCommit` | boolean | `false` | Timestamp every meaningful commit (§6.1) |
| `ots.maxAge` | duration | `24h` | Timestamp when the oldest pending commit exceeds this age (§6.2) |
| `ots.fixedTime` | time of day | unset | Timestamp at a fixed daily time (§6.3) |
| `ots.timezone` | IANA zone | unset | Zone qualifying `ots.fixedTime` (§6.3) |
| `ots.initialHistory` | `latest` \| `all` | `latest` | What to timestamp on a repository with no prior baseline (§18) |
| `ots.sourceRef` | ref | `HEAD` | The ref whose history is timestamped (§15, §16) |
| `ots.fetchBeforeRun` | boolean | `true` | Fetch before resolving the source ref |
| `ots.tagPrefix` | string | `ots/` | Prefix for timestamp tags |
| `ots.requireCleanWorktree` | boolean | `false` | Refuse to run with a dirty worktree (§25) |
| `ots.signing` | `inherit` \| `required` | `inherit` | Signing of the objects this tool creates |
| `ots.proofCommit` | boolean | `true` | Commit proof artifacts (§13) |
| `ots.proofDirectory` | path | `.opentimestamps` | Where proofs and manifests are stored (§4) |
| `ots.squashUpgradeCommits` | boolean | `false` | Fold a new upgrade commit into the previous one (§28.6.2) |
| `ots.command` | string | `ots` | The OpenTimestamps client to invoke |
| `ots.otsTimeout` | duration | `120s` | Bound on one `ots` submission or upgrade |
| `ots.gitTimeout` | duration | `60s` | Bound on one `git` invocation |

`ots.proofDirectory` SHALL be repository-relative, SHALL NOT end with `/`, and
SHALL NOT name any location outside the worktree — an absolute path, a `..` or
`.` segment, an empty segment, a leading `~`, or a backslash SHALL be rejected
(§31). Its value reaches Git pathspecs, timestamp-tag annotations (§12), and
`git ls-tree` output the tool parses back, so each path segment SHALL further
be restricted to `[A-Za-z0-9._-]+`.

Moving the proof directory is a discovery hazard and SHALL be understood as
one. Configuration lives only in Git config, which a clone never
receives, so nothing in a repository can tell a consumer that its proofs are
not in the default location; they have to be told out of band. A previous
revision of this document removed the setting outright for that reason. It is
restored because the hazard is the operator's to accept, not the tool's to
forbid — but the default remains `.opentimestamps/`, and it is the location
every consumer is entitled to assume absent other information.

Changing the value SHALL NOT migrate the proofs already written; moving them is
the operator's responsibility. The consequences of not moving them follow from
the rest of this specification and are stated here so they are not discovered
in production. Proof scanning (§28.4, §28.5, §28.6) reads only the configured
directory, so proofs left in the previous one become invisible to `validate`,
`verify`, `upgrade`, and `status`. Tag-derived baselines (§17) are unaffected,
because a tag records the source commit and ancestry rather than a path. Proof-commit
baselines are not: the manifest is read from the configured directory,
so it is not found, and a generated proof commit that still claims the source
without reachable recovery artifacts is the inconsistent state §22.3 requires
be reported rather than silently re-timestamped. Since tags are never pushed,
this is the state every consumer of the repository sees.

Booleans SHALL be resolved by Git's own boolean vocabulary — `true`/`false`,
`yes`/`no`, `on`/`off`, `1`/`0`, and a valueless key, which Git reads as true —
rather than by a table this tool implements. A value Git rejects as a boolean
SHALL fail with the invalid-configuration exit code, and the diagnosis SHALL be
Git's own.

`ots.otsTimeout` and `ots.gitTimeout` bound the wall-clock duration of the
external `ots` and `git` subprocesses the tool invokes. `ots.otsTimeout` SHALL
bound a single OpenTimestamps submission, upgrade, or verification;
`ots.gitTimeout` SHALL bound a single `git` invocation, except for reads of file content out of a
commit tree (`git show <commit>:<path>`, `git cat-file --batch`) and the
repository-location lookup (`git rev-parse --show-toplevel`, `git rev-parse
--git-common-dir`), both of which are always bounded by the built-in default
regardless of this setting. The location lookup runs *before* any configuration
has been read — it is what makes reading it possible — so it cannot be bounded
by a value it has not yet obtained.

Both SHALL accept the duration syntax of §6.2, plus the literal string `0`,
which SHALL mean unbounded — no ceiling is applied. The `0` spelling SHALL be
recognized only for these two keys; it SHALL NOT be accepted as an unbounded
escape hatch for `ots.maxAge` or any other duration-valued setting.

An unconfigured repository is a valid repository: with no `ots.*` key set in
any scope, the defaults above apply and the tool SHALL run without complaint.

# 6. Policy configuration

## 6.1 `every_commit`

```text
git config ots.everyCommit false
```

Type:

```text
boolean
```

When enabled, every pending meaningful commit SHALL receive an independent OpenTimestamps proof.

Generated proof commits SHALL still be ignored.

Because several source commits may have accumulated between invocations, enabling `every_commit` means that one invocation MAY submit multiple commits.

Example:

```text
timestamp A
commit B
commit C
commit D
run git ots
```

With:

```text
git config ots.everyCommit true
```

the invocation timestamps:

```text
B
C
D
```

in repository order.

With:

```text
git config ots.everyCommit false
```

an aggregate trigger timestamps only:

```text
D
```

---

## 6.2 `max_age`

Example:

```text
git config ots.maxAge 24h
```

Supported duration syntax SHOULD include:

```text
45s
30m
12h
24h
2d
7d
```

A disabled value MAY be represented by omission.

The rule becomes due when:

```text
current_time >= oldest_pending_commit_time + max_age
```

The timestamp target SHALL be the latest pending meaningful commit.

Therefore:

```text
01:00 commit B
10:00 commit C
25:00 policy fires
```

timestamps C, not B.

Timestamping C also covers B as part of the Git history.

### Time source

Git does not record the time at which a commit was pushed to a remote.

Therefore the maximum-age calculation SHALL, by default, use the Git **committer timestamp**.

The author timestamp SHALL not be used.

Consequently, the guarantee concerns age relative to the commit metadata rather than exact remote push time.

---

## 6.3 `fixed_time`

Example:

```text
git config ots.fixedTime 00:00
git config ots.timezone Europe/Berlin
```

The timezone SHALL be exact `UTC` or a slash-qualified IANA timezone
identifier. This portable spelling rule SHALL be applied before consulting the
host timezone database so platform-specific aliases do not alter validation.

Examples:

```text
Europe/Berlin
UTC
America/New_York
```

The configured local time identifies one daily schedule occurrence.

A fixed-time occurrence becomes eligible at:

```text
configured local time
```

and remains eligible until the next schedule occurrence.

The implementation SHALL therefore not require execution during one exact minute.

For example, with:

```text
git config ots.fixedTime 00:00
```

an invocation at:

```text
00:03
```

may satisfy the midnight occurrence if it has not yet been satisfied.

This prevents missed timestamps merely because cron, CI, or another scheduler was delayed.

### Fixed-time condition

A fixed-time timestamp SHALL only be created when meaningful pending changes exist.

No-change case:

```text
00:00  timestamp A
next day 00:00
```

with no source changes:

```text
no submission
no proof
no commit
no tag
```

# 7. Combining policies

All enabled policies SHALL be evaluated independently.

Their triggers combine using logical OR.

Conceptually:

```text
pending_changes =
    one or more meaningful commits are pending

should_timestamp =
    every_commit
    OR (pending_changes AND max_age_due)
    OR (pending_changes AND fixed_time_due)
```

For aggregate policies, if several rules become due during one invocation, they SHALL produce only one submission for the current latest source state.

Example:

```text
max_age_due   = true
fixed_time_due = true
latest_commit = D
```

Result:

```text
one OpenTimestamps submission for D
```

The metadata SHOULD record both reasons:

```json
{
  "triggers": [
    "max_age",
    "fixed_time"
  ]
}
```

# 8. Policy semantics

## 8.1 No meaningful changes

Given:

```text
last timestamped source = A
current source history  = A + proof commit
```

result:

```text
do nothing
```

regardless of maximum age or fixed time.

---

## 8.2 Meaningful changes, but no trigger

Given:

```text
last timestamp = A at 00:00
commit B       = 01:00
current time   = 12:00
max_age        = 24h
fixed_time     = 00:00
```

result:

```text
do nothing
```

---

## 8.3 Maximum age reached

Given:

```text
commit B = day 1 01:00
commit C = day 1 15:00
now      = day 2 01:00
max_age  = 24h
```

result:

```text
timestamp C
```

The oldest pending state B has reached the maximum allowed age, but the newest state C is the state actually timestamped.

---

## 8.4 Fixed-time trigger

Given:

```text
previous timestamp = yesterday 00:00
commit B           = 08:00
commit C           = 19:00
run                 = today 00:01
fixed_time          = 00:00
```

result:

```text
timestamp C
```

---

## 8.5 Multiple policy triggers

Given:

```text
max_age_due    = true
fixed_time_due = true
```

result:

```text
one timestamp
```

not two.

---

## 8.6 Every-commit policy combined with aggregate policies

`every_commit` has stronger target-selection semantics.

If enabled, all pending meaningful commits SHALL be timestamped individually.

Example:

```text
A already stamped
B pending
C pending
D pending
```

produces proofs for:

```text
B
C
D
```

The aggregate policies become operationally redundant for those commits but MAY remain enabled in the configuration.

# 9. Timestamp subject

The object being timestamped SHALL be the Git source commit identifier.

Because Git repositories may use different object hash formats, the representation SHALL be explicit and versioned.

A canonical payload SHOULD be defined as:

```text
git:<object-format>:<full-commit-id>\n
```

Examples:

```text
git:sha1:0123456789abcdef0123456789abcdef01234567
```

or:

```text
git:sha256:<64-character-hash>
```

followed by exactly one LF byte.

The canonical representation prevents ambiguity between:

* SHA-1 repositories;
* SHA-256 repositories;
* textual versus binary commit IDs;
* future payload formats.

The manifest SHALL record the payload format version.

---

# 10. OpenTimestamps integration

OpenTimestamps functionality SHALL be isolated behind an adapter.

The policy and Git modules SHALL not directly depend on OpenTimestamps command syntax.

Conceptually:

```python
proof = timestamp_client.submit(payload)
```

The adapter is responsible for:

1. producing the canonical timestamp payload;
2. submitting it to OpenTimestamps;
3. obtaining the detached proof;
4. ensuring the proof is non-empty and structurally valid;
5. writing it to the configured proof location;
6. reporting success or failure.

A successful process exit alone SHOULD NOT be considered sufficient if no proof file was produced.

No Git tag SHALL be created until a proof has successfully been written.

# 11. Proof storage

For source commit:

```text
0123456789abcdef...
```

the default files SHALL be:

```text
.opentimestamps/0123456789abcdef....ots
.opentimestamps/0123456789abcdef....json
```

The full Git object ID SHALL be used in filenames.

`.opentimestamps/` is `ots.proofDirectory`'s default (§5); when it is set to
another value both files SHALL be written under that directory instead. Only
the directory changes — the file names, the manifest schema, and the proof
bytes do not depend on where they are stored.

## 11.1 Proof manifest

Example:

```json
{
  "schema": 1,
  "source_commit": "0123456789abcdef0123456789abcdef01234567",
  "git_object_format": "sha1",
  "payload_format": "git-commit-id-v1",
  "submitted_at": "2026-08-09T00:00:03Z",
  "proof": "0123456789abcdef0123456789abcdef01234567.ots",
  "source_ref": "origin/master",
  "triggers": [
    "fixed_time"
  ]
}
```

`submitted_at` SHALL be stored in UTC using RFC 3339.

The manifest is operational metadata.

The OpenTimestamps proof remains the cryptographic evidence.

# 12. Git tags

Every successful timestamp submission SHALL produce an annotated Git tag pointing directly at the source commit.

Recommended format:

```text
ots/<UTC-timestamp>/<short-sha>
```

Example:

```text
ots/20260808T220003Z/0123456789ab
```

The commit SHA component prevents collisions if several commits are timestamped during the same second.

The tag annotation SHOULD contain:

```text
git-ots schema: 2
producer: git-ots 0.0.1
source: 0123456789abcdef0123456789abcdef01234567
submitted-at: 2026-08-08T22:00:03Z
proof: .opentimestamps/0123456789abcdef0123456789abcdef01234567.ots
triggers: fixed_time
```

Tags SHALL be immutable from the perspective of `git-ots`.

New tags SHALL use annotation schema 2 and record the producing git-ots
version. Readers SHALL continue accepting schema-1 tags, which have no
`producer` field. This field is descriptive metadata: it does not change the
canonical timestamp payload or proof-manifest schema.

The program SHALL never automatically move or overwrite an existing timestamp tag.

## 12.1 Signatures in the annotation

Git stores a tag signature inside the tag body, after the annotation. Every
reader of an annotation therefore sees it, whether the signature was requested
by `signing = "required"` or by ambient Git configuration such as
`tag.gpgSign`.

An implementation SHALL strip a trailing ASCII-armored signature block before
parsing or comparing an annotation. Armored signatures may carry headers
(`Version:`, `Comment:`) whose shape is indistinguishable from an annotation
field, and the schema above admits no extra keys, so an unstripped signature
makes a valid tag read as malformed — removing it from consideration as a
timestamp baseline and causing its source commit to be timestamped again.

A tag collision SHALL be treated as an error unless the existing tag is demonstrably identical to the intended state.

# 13. Generated proof commits

Proof material SHALL be committed when:

```text
git config ots.proofCommit true
```

The commit SHALL be clearly machine-identifiable.

Recommended commit message:

```text
Store OpenTimestamps proof for 0123456789ab

OpenTimestamps-Generated: true
OpenTimestamps-Source: 0123456789abcdef0123456789abcdef01234567
```

For a batch:

```text
Store OpenTimestamps proofs

OpenTimestamps-Generated: true
OpenTimestamps-Source: <sha-1>
OpenTimestamps-Source: <sha-2>
```

The canonical generated-commit marker SHALL be:

```text
OpenTimestamps-Generated: true
```

in the commit trailers.

A generated proof commit SHALL be recognized by the presence of that trailer
alone. Because the trailer is written atomically with the commit object, it is
stable across reconfiguration of `proof.directory`, unlike a path-only check.

If a trailer-bearing commit also changes paths outside the configured proof
directory, the program SHOULD emit a warning to stderr so the case is visible
rather than silently ignored. The warning SHALL NOT change the command exit code.


---

# 14. Determining meaningful commits


A commit SHALL be ignored as generated metadata only if its commit message
contains the canonical generated trailer:

```text
OpenTimestamps-Generated: true
```

Conceptually:

```text
generated = has_generated_trailer
```

Everything else is meaningful.

Therefore:

```text
user manually edits .opentimestamps/foo.ots
```

in an ordinary commit:

```text
meaningful = true
```

This avoids silently excluding real repository modifications merely because they affect the proof directory.

The previous two-condition rule (trailer plus proof-directory-only changes)
was revised because it reclassified every historical proof commit as
meaningful whenever `proof.directory` was reconfigured. Trailer-only
recognition is stable across reconfiguration.

Because the trailer alone is now sufficient to ignore a commit, a forged or
squashed trailer could mask real work. The program SHALL emit a warning to
stderr when a trailer-bearing commit also changes paths outside the configured
proof directory, so the case is visible instead of silent. The warning does not
change the command exit code.

# 15. Source ref

Default:

```text
git config ots.sourceRef HEAD
```

The source ref determines which repository history is eligible for timestamping.

The program SHALL resolve it to a concrete commit before policy evaluation.

When:

```text
git config ots.fetchBeforeRun true
```

the program SHALL fetch the relevant remote before resolving the source ref.

The fetch operation SHALL not merge, rebase, checkout, or otherwise modify the worktree.



---

# 16. Source ref default

Default:

```text
git config ots.sourceRef HEAD
```

The source ref determines which repository history is eligible for timestamping.

By default, the eligible state is the current branch tip. This makes stamping
before publication a first-class use case: a Git commit hash is identical
whether it exists on a laptop or a forge, so the remote is not a cryptographic
trust boundary.

Users who prefer to timestamp only pushed state may configure:

```text
git config ots.sourceRef '@{upstream}'
```

That upstream-only mode is a churn-and-cost preference, not a safety property:
it avoids leaving permanent timestamp tags on amended, squashed, or rebased
local commits, and it avoids paying for submissions whose hashes may never be
referenced elsewhere.

# 17. Finding the timestamp baseline

The program SHALL inspect tags matching the configured tag prefix.

For normal aggregate operation, it must identify the newest relevant timestamped source commit that is part of the source history.

Conceptually:

```text
timestamp tags
    ↓
tags whose targets are ancestors of source_ref
    ↓
latest relevant timestamp state
```

Meaningful commits after that state are pending.

Generated proof commits in that range are filtered out.

---

# 18. Initial repository behavior

If no timestamp tag exists, the repository has no baseline.

For aggregate policies:

* existing meaningful history SHALL be treated as pending;
* `fixed_time` MAY timestamp the latest source commit when its next occurrence is due;
* `max_age` MAY timestamp immediately if the oldest meaningful commit already exceeds the configured age.

For `every_commit`, blindly timestamping an entire long repository history may be undesirable.

Therefore the initial invocation SHOULD support one of two explicit behaviors:

```text
git config ots.initialHistory latest
```

or:

```text
git config ots.initialHistory all
```

Recommended default:

```text
git config ots.initialHistory latest
```

Meaning:

* aggregate policies timestamp the latest state;
* `every_commit` timestamps every meaningful commit only after the initial baseline has been established.

This avoids unexpectedly submitting thousands of historical commits when enabling the tool on an existing repository.

---

# 19. Fixed-time occurrence tracking

A fixed-time schedule SHALL be interpreted in the configured timezone.

For:

```text
git config ots.fixedTime 00:00
git config ots.timezone Europe/Berlin
```

an occurrence can be represented internally as:

```text
2026-08-09T00:00:00+02:00
```

The policy SHALL determine the most recent scheduled occurrence at or before the current time.

A fixed-time occurrence is actionable only if:

1. it has not already been satisfied; and
2. meaningful changes are pending.

A timestamp produced during an invocation where the fixed-time rule is due SHALL mark that occurrence as satisfied.

The trigger metadata stored in the tag and manifest provides sufficient evidence for this determination.

Timezone calculations SHALL correctly handle daylight-saving transitions.

The implementation SHALL use timezone-aware datetime objects exclusively.

---

# 20. Idempotency

Repeated execution SHALL be safe.

Given identical repository and configuration state:

```text
run #1 → timestamp created
run #2 → no action
run #3 → no action
```

The second invocation SHALL recognize:

* the source commit tag;
* the proof metadata;
* the generated proof commit;

and conclude that there are no pending meaningful changes.

Idempotency also applies to overlapping triggers.

A source state SHALL never receive multiple submissions merely because:

```text
max_age_due == true
fixed_time_due == true
```

during the same evaluation.

The baseline is derived from the newest relevant timestamped source, whether
identified by an annotated tag or by a generated proof commit manifest that
names an ancestor of the frozen source. When both kinds of evidence exist, the
newest by `submitted_at` SHALL prevail.


---

# 21. Operation ordering

For each source commit selected for timestamping, side effects SHALL occur in this order:

```text
1. resolve and freeze source commit ID
2. construct canonical payload
3. submit to OpenTimestamps
4. obtain proof
5. write proof to temporary file
6. validate proof exists and is non-empty
7. atomically move proof into final location
8. write manifest
9. stage proof and manifest
10. commit proof and manifest
11. create annotated source tag
```

The source ref SHALL NOT be re-resolved between steps 1 and 11.

This prevents a concurrently advancing branch from changing the identity of the commit being timestamped midway through an invocation.

The generated proof commit precedes the annotated source tag so that a tag is never created unless the proof artifacts are already committed. This ordering also makes the "tag present, proof commit absent" crash-recovery state impossible, because the tag is created only after the commit succeeds.

Steps 3 to 11 SHALL be treated as one resumable transaction rather than as a
sequence a failed step ends. Before acting on the policy decision, an
invocation SHALL complete any transaction an earlier invocation left open (see
section 22.4) and SHALL NOT begin a new submission in the same invocation. A
run that submits while an earlier submission remains unrecorded races the
repository instead of converging on it: because the source ref is re-resolved
on every invocation, a run blocked long enough succeeds against a different commit and
abandons the commitment already paid for.


---

# 22. Crash recovery

The tool SHALL tolerate interruption between operations.

## 22.1 Proof exists, tag absent

Possible cause:

```text
process terminated after proof write
```

On the next run, the program SHOULD inspect the manifest and proof.

If they validly describe the intended source commit, it SHOULD continue the transaction rather than resubmitting unnecessarily.

## 22.2 Tag exists, proof files uncommitted

This state cannot occur under the ordering in section 21, because the source tag is created only after the generated proof commit succeeds. It is documented here only as a superseded historical crash state.

If tooling encounters a tag with uncommitted proof files, the operator must resolve the inconsistency manually; the implementation MUST NOT silently create another timestamp.

## 22.3 Proof artifacts are committed, tag absent

Possible causes:

```text
process terminated between the proof commit and the tag
the proof commit was rejected and the artifacts reached history by another route
a clone, which carries proof commits but no tags
```

The implementation SHALL create the missing tag when, and only when, the
manifest and the proof it names are both readable from the frozen source
commit's tree, the manifest satisfies the schema in section 11.1, and the proof
binds to the canonical payload for the source the manifest claims.

The condition SHALL be stated in terms of that evidence, not in terms of a
generated proof commit carrying a matching `OpenTimestamps-Source` trailer.
Reading the artifacts from the source tree already establishes that they are
committed, which is the precondition section 21's ordering attaches to tagging;
that precondition is about durability in history and is indifferent to which
commit provided it. A trailer is a claim, whereas a payload binding is a proof,
so requiring the trailer is both weaker and — because the two conditions can
diverge — a route to a permanently untagged proof.

`submitted_at`, `source_ref` and the trigger set SHALL come from the manifest.
The implementation MUST NOT substitute the recovery time for `submitted_at`.

Where a generated proof commit claims a source but no valid manifest can be
found, the state is inconsistent. The implementation SHALL inspect the manifest
and determine whether it represents a successful submission. It MUST NOT guess
silently. If a safe recovery cannot be established, the command SHALL fail with
an actionable error.


## 22.4 Submission recorded on disk, tag absent

Possible cause:

```text
the generated proof commit failed after the proof was written
```

This is an **in-flight** submission: a commitment the calendars hold and the
repository does not record. It is distinct from section 22.3 in that the
artifacts have not reached history at all — they are typically staged, because
`git add` succeeded and `git commit` did not.

A source is in flight when its proof and manifest are present and valid in the
working tree, the proof binds to the canonical payload for that source, the
source is an ancestor of the frozen source commit, and **no timestamp tag names
it**.

A source that carries a timestamp tag SHALL NOT be treated as in flight,
whatever the state of its artifacts. The tag is the record of the submission;
whether the artifacts are additionally committed is governed by
`ots.proofCommit` and is section 22.2's concern. Treating a tagged source as in
flight would sweep artifacts stamped under `ots.proofCommit = false` into a
generated proof commit made by a later run with the key enabled.

Before acting on the policy decision, an invocation SHALL commit and tag every
in-flight source, and SHALL NOT submit anything in the same invocation. The
paths of every in-flight source SHALL be included in the generated proof
commit's pathspec, so that a successful commit never leaves an earlier
submission's artifacts staged and unreferenced.

An implementation SHALL report a deferred submission rather than silently
omitting it; the work is delayed by one invocation, never dropped.


## 22.5 Reconciling proofs no invocation will reach

Section 22.3 and section 22.4 are evaluated for the baseline, the pending
sources, and the in-flight sources. A stored proof outside all of those — an
older stamp orphaned by an interruption long since passed — has no automatic
route back.

The implementation SHALL provide a command that creates the missing tag for
every stored proof whose source resolves and is an ancestor of the frozen
source, reconstructing the annotation from the manifest under the binding check
of section 22.3. It SHALL NOT re-submit, SHALL NOT move or overwrite an
existing tag (section 12), and SHALL NOT manufacture a submission time.

Proofs whose source does not resolve, or is not an ancestor of the frozen
source, SHALL be reported and left alone. Creating a tag on an abandoned
lineage changes what the baseline search of section 20 observes and can trigger
the rewritten-history refusal of section 26.

# 23. Atomic filesystem writes

Proof and metadata files SHALL be written atomically.

Recommended pattern:

```text
write temporary file
fsync if appropriate
rename into final path
```

Partial `.ots` or `.json` files SHALL never be treated as valid completed proofs.

# 24. Concurrency

Only one `git-ots` process SHALL modify a repository at a time.

The implementation SHALL acquire an advisory repository-level lock before performing policy evaluation or side effects.

The lock SHOULD reside in the Git common directory rather than the working tree.

Conceptually:

```text
.git/git-ots.lock
```

or the equivalent common Git directory for linked worktrees.

If another active process holds the lock, a second invocation SHALL exit without attempting timestamp submission.

A stale pathname alone SHALL not permanently lock the repository; ownership should use an OS-level or otherwise automatically releasable locking mechanism.

---

# 25. Worktree safety

When proof commits are enabled, the implementation SHALL require a committable
repository state before modification. In-progress operations such as
`MERGE_HEAD`, `CHERRY_PICK_HEAD`, `rebase-merge/`, `rebase-apply/`, or a detached
HEAD when `proof.commit = true` SHALL produce an actionable error with zero
submissions.

The `require_clean_worktree` key remains available as an operator preference.
It SHALL default to `false`. The proof commit's exclusion of unrelated
modifications is structural -- it follows from the explicit-pathspec
requirement below -- so the key confers no safety the implementation does not
already guarantee. All a default of `true` could add is refusal, and on the
scheduled path a refused run is a timestamp silently not taken whenever the
operator has work in progress.

When set to `true`, unrelated uncommitted changes SHALL cause failure before
submission:

```text
git config ots.requireCleanWorktree true
```

The implementation SHALL stage only explicitly generated proof and manifest paths.

It SHALL never use:

```text
git add .
```

or equivalent broad staging.


---

# 26. Git history changes

Force pushes, rebases, and history rewrites require special handling.

The baseline is derived from the newest relevant timestamped source that is an
ancestor of the frozen source ref, whether identified by an annotated tag or by
a generated proof commit manifest. A proof commit carried onto a new lineage by a
history rewrite is rejected as a baseline if its manifest names a source that is
no longer an ancestor of the frozen source.

If a previous timestamp tag references a commit that is no longer an ancestor of the configured source ref:

* the tag SHALL remain untouched;
* it still represents a valid historical OpenTimestamps record;
* the current source history SHALL be evaluated separately.

For aggregate policies, the latest current state MAY be timestamped as a new lineage.

For `every_commit`, the tool SHOULD fail rather than implicitly timestamp an entire rewritten history.

Existing timestamp tags SHALL never be deleted automatically.


---

# 27. Proof upgrades

OpenTimestamps proofs may later gain stronger attestations or be upgraded.

Proof upgrading is outside the core timestamp-trigger policy.

If proof-upgrade support is implemented, any resulting commit SHALL use the same generated-commit marker:

```text
OpenTimestamps-Generated: true
```

and SHALL therefore not count as a meaningful source change.

Updating an existing `.ots` file SHALL not change the original source tag.

Consecutive upgrade commits MAY be collapsed into one, at the operator's
explicit request and under the conditions of §28.6.2.

# 28. CLI

The executable SHALL be named:

```text
git-ots
```

## 28.1 Defaults

Configuration SHALL be optional. Every setting SHALL have a built-in default,
and the tool SHALL operate on a repository that has never been configured — one
with no `ots.*` key set in any Git config scope.

The default policy SHALL be:

```text
git config ots.maxAge 24h
```

Naming any other trigger SHALL replace that default rather than add to it: a
configuration that sets `ots.everyCommit` or `ots.fixedTime` and does not set
`ots.maxAge` SHALL have no maximum-age trigger. Where triggers are named at
more than one Git config scope, the narrowest scope naming any *enabling*
trigger determines the trigger set entirely, and triggers named only at a wider
scope are discarded rather than merged (§5, §6).

There SHALL NOT be a subcommand that writes configuration. `git config` is
already the way a key is set, and a bootstrap subcommand would either duplicate
it or write a file into the worktree — which would make the worktree dirty, and
the cleanliness precondition of §25 then refuses to run against it. A default
copied into storage at setup time also cannot be revised for repositories
already configured. The defaults of §5 are therefore the only statement of what
an unconfigured repository does.

`git ots config` (§28.8) reads the effective configuration back; it does not
write.

## 28.2 Run

Primary command:

```text
git ots run
```

There is no configuration-file flag. Configuration is read from Git config
(§5), so the ordinary Git mechanisms override it for a single invocation
without the tool providing one of its own:

```text
git -c ots.maxAge=1h ots run
```

`run` both timestamps and reconciles. Before acting on the policy decision it
completes any transaction an earlier invocation left open (sections 22.3 and
22.4). It SHALL report on stdout when it has done so, so that a run which
repaired the repository is not indistinguishable from one that found nothing
to do.

An opt-in flag SHALL make the "nothing was due and nothing was repaired"
outcome distinguishable by exit code (§29):

```text
git ots run --exit-code
```

## 28.3 Dry run

```text
git ots run --dry-run
```

Dry-run mode SHALL:

* resolve repository state;
* evaluate policies;
* display selected commits;
* display trigger reasons;

but SHALL NOT:

* contact OpenTimestamps;
* create files;
* create tags;
* create commits.

## 28.4 Status

A read-only status command SHOULD be provided:

```text
git ots status
```

It SHOULD report information such as:

```text
source ref:              origin/master
source commit:           abcdef123456
last timestamped source: 123456abcdef
pending meaningful:      4
oldest pending age:      18h 32m
max-age trigger:         not due
fixed-time trigger:      due at next 00:00 Europe/Berlin
```

### 28.4.1 Anchor reporting

Status SHALL additionally report, for every stored proof, where that proof is
anchored. For each Bitcoin block header attestation it SHALL report the block
height, the calendar that published it, the identifier of the Bitcoin
transaction carrying the commitment, the commitment pushed by that
transaction's `OP_RETURN` output, and the block merkle root.

Calendars that promised a proof but whose branch carries no Bitcoin
attestation SHALL be reported as outstanding, whether or not the proof is
already anchored, because `git ots upgrade` asks each of them on every run
(section 28.6.1). Status SHALL NOT report as outstanding anything that upgrade
would not attempt, nor omit anything it would.

Status and upgrade SHALL both report, per proof, how many of the calendars it
was submitted to published an anchor, out of how many were asked. This ratio
SHALL be understood as realized redundancy rather than progress: because the
client stops at the first Bitcoin attestation, a complete proof normally
remains below its denominator permanently. It is not a count of Bitcoin
confirmations, which a stored proof does not record.

Every reported value SHALL be derived from the stored proof alone, by
executing the proof's operations:

* the block height is stored in the attestation payload;
* the block merkle root is the message reaching that attestation;
* the transaction identifier is the double-SHA-256 of whichever message along
  the path deserializes as a Bitcoin transaction, in the legacy
  (non-witness) serialization the identifier is defined over;
* the `OP_RETURN` commitment is read from that transaction's outputs.

The calendar that published an anchor is identifiable because an upgrade
appends the path to Bitcoin *below* the pending attestation rather than
replacing it, and because every attestation at a node is serialized before
that node's operations. A calendar promise therefore applies to the branches
that follow it.

This reporting SHALL NOT contact Bitcoin or verify the anchor against a block.
It reports what the proof claims; confirming the claim on-chain is `ots
verify`'s job.

### 28.4.2 Calendar reachability

Status SHALL NOT perform network access by default, because it is the command
a scheduler runs and must not become dependent on network conditions.

An opt-in flag SHALL probe the calendars named by stored proofs:

```text
git ots status --check-servers
```

`git-ots` does not configure calendars -- the OpenTimestamps client owns that
-- so the servers subject to the check are exactly those named in this
repository's proofs, which are the ones its pending proofs depend on. Each
calendar SHALL be reported as reachable or unavailable, and an unavailable
calendar SHALL additionally produce a warning naming how many stored proofs
are waiting on it. A calendar that answers any HTTP status SHALL count as
reachable; only a transport-level failure counts as unavailable. Calendar URLs
originate in proof files, so a URL whose scheme is not `http` or `https` SHALL
be reported as unavailable and SHALL NOT be opened.

An unavailable calendar SHALL NOT change the command exit code: it is
information about the world, not a malfunction.

## 28.5 Validate and verify

A read-only, offline validation command SHALL inspect every stored proof in the
configured proof directory:

```text
git ots validate
```

For each proof it SHALL report one of:

* `valid` — structurally valid, bound to the attested source commit, and that
  commit is an ancestor of the current source ref;
* `orphaned` — valid and bound, but the attested commit is no longer an ancestor
  of the current source ref;
* `pending-attestation` — structurally valid and bound, but contains only
  calendar attestations and no Bitcoin block attestation;
* `invalid` — malformed, unbound, or otherwise failing validation;
* `unknown-source` — the attested commit cannot be resolved (for example, because
  it has been garbage-collected). This is a distinct state, not a variety of
  `orphaned`: `git merge-base --is-ancestor` *errors* on an object the
  repository no longer has rather than answering false, so an unresolvable
  source SHALL be resolved before, and reported separately from, the ancestry
  test.

For each proof it SHALL additionally report whether the repository carries a
timestamp tag naming the attested source commit. This is reported alongside the
state rather than as another state: the states above are mutually exclusive
claims about the proof, whereas the presence of a tag is an orthogonal fact
about bookkeeping, and a proof can be both `orphaned` and untagged.

A missing tag SHALL NOT change the command's exit code. Timestamp tags are
never pushed (section 12), so a clone legitimately carries generated proof
commits and no tags at all; the reporting requirement exists because proof
state and tag state could otherwise diverge with no diagnostic naming it.

The command SHALL NOT create, delete, or modify any tag, commit, or file, and
SHALL NOT perform network access. A `valid` result means locally valid and
Bitcoin-attested; it SHALL NOT be described as chain-confirmed.

A separate verification command SHALL perform the final chain-backed check:

```text
git ots verify
```

It SHALL first perform the same local validation, reconstruct the canonical
payload, and delegate each Bitcoin-attested proof to the configured
OpenTimestamps client's `verify` operation. It SHALL report `verified` only
after that client successfully checks the attestation against a Bitcoin block.
Pending proofs SHALL be reported as `pending-attestation` without invoking the
client. A client or node failure SHALL be reported as `verification-failed`,
not as proof invalidity. Verification SHALL NOT modify repository artifacts.

## 28.5.1 Repair

A command SHALL reconcile stored proofs with the tags that record them:

```text
git ots repair [--dry-run]
```

It implements section 22.5. For each stored proof whose source resolves, is an
ancestor of the frozen source commit, and carries no timestamp tag, it SHALL
create the annotated tag defined in section 12, taking `submitted_at`, the
proof path and the trigger set from the manifest, after validating the
manifest against section 11.1 and the proof's binding to the canonical payload.

It SHALL NOT submit to any calendar, SHALL NOT move or overwrite an existing
tag, and SHALL NOT manufacture a submission time. A proof whose manifest cannot
be validated SHALL be reported and SHALL NOT stop the remaining proofs from
being repaired; the command SHALL exit with the proof-persistence code when any
such proof is found. With `--dry-run` the command SHALL create nothing and
report what it would create.


## 28.6 Upgrade

An upgrade command SHALL complete stored proofs that carry only calendar
attestations:

```text
git ots upgrade [--dry-run]
```

With `--dry-run` the command SHALL contact no calendar and write nothing, and
SHALL report for each proof what a real pass would attempt.

The command SHALL select every proof in the configured proof directory that
parses, binds to the source commit named by its manifest, and contains no
Bitcoin block header attestation. Ancestry SHALL NOT affect selection: a proof
whose source commit has left the source ref's lineage is still a timestamp of a
real commit.

For each selected proof it SHALL report one of:

* `upgraded` — new attestations were obtained and the proof file was rewritten;
* `still-pending` — no calendar had anything new to contribute;
* `already-complete` — a Bitcoin block header attestation is already present;
* `skipped` — the proof or its manifest is malformed or unbound.

The upgrade SHALL be performed on a copy outside the repository, and the
result SHALL be written back through the same atomic-write boundary used for
new proofs. An upgraded proof SHALL be stored only if it still binds to the
canonical payload of the same source commit. The command SHALL NOT create,
delete, or modify any tag, SHALL NOT resubmit, and SHALL NOT rewrite manifests:
`submitted_at` records the submission, not the upgrade.

The OpenTimestamps client's exit status SHALL NOT be treated as the outcome:
the client reports failure both when no calendar can complete a proof yet and
when a real error occurs. The resulting file content is the outcome, and the
client's diagnostic SHALL be surfaced in the `still-pending` report so an
unreachable calendar is distinguishable from one that is not yet ready.

When `[proof] commit` is enabled, rewritten proof files SHALL be committed as a
single generated commit carrying `OpenTimestamps-Generated: true`, so that
proof maintenance is never itself a meaningful commit. Upgraded
sources SHALL be named with an `OpenTimestamps-Upgraded` trailer rather than
`OpenTimestamps-Source`, because the source trailer denotes the claim to have
stamped a commit and an earlier proof commit already carries it.

The message SHALL be, for a single source:

```text
Upgrade OpenTimestamps proof for 0123456789ab

OpenTimestamps-Generated: true
OpenTimestamps-Upgraded: 0123456789abcdef0123456789abcdef01234567
```

and for several, with the count in the subject:

```text
Upgrade 3 OpenTimestamps proofs

OpenTimestamps-Generated: true
OpenTimestamps-Upgraded: <sha-1>
OpenTimestamps-Upgraded: <sha-2>
OpenTimestamps-Upgraded: <sha-3>
```

Unlike §13's, this message shape is normative rather than recommended:
§28.6.2 reads it back to decide whether a commit may be amended, so a
different spelling is a commit this tool declines to treat as its own.

### 28.6.1 Collecting attestations the client will not

The OpenTimestamps client treats a timestamp as complete at its first Bitcoin
attestation and stops upgrading, so calendars that confirm later are never
asked again and their attestations never reach the file. A stored proof would
then claim less than actually happened.

After the client has run, the upgrade command SHALL therefore ask every
calendar that has promised a proof and whose branch carries no Bitcoin
attestation, using the commitment that calendar was given -- recovered by
executing the proof's operations to that pending attestation -- and SHALL merge
any timestamp returned into the proof at that node.

Merging SHALL be additive: it SHALL add attestations and operations that are
not already present and SHALL NOT rewrite or remove existing ones. Merging a
response the proof already contains SHALL be a no-op, so repeated upgrades
converge.

Before a merged proof replaces a stored one it SHALL be revalidated: it SHALL
still bind to the canonical payload of the same source commit, and it SHALL
still contain every attestation the stored proof contained. A response that
cannot be parsed, or that fails either check, SHALL be discarded and the stored
proof SHALL be left untouched.

`git ots run` SHALL NOT perform upgrades or collection. Both require network
access and rewrite existing artifacts, so they remain explicitly
operator-invoked.

### 28.6.2 Squashing consecutive upgrade commits

A proof rarely gains every attestation it will ever have in one pass, so a
repository upgraded on a schedule accumulates a run of upgrade commits that
each restate the same claim about the same files. When

```text
git config ots.squashUpgradeCommits true
```

is set, an upgrade that would create a commit SHALL instead amend the commit
at `HEAD`, provided every one of the following holds:

* `HEAD` carries at least one `OpenTimestamps-Upgraded` trailer;
* `HEAD`'s message is, ignoring trailing newlines, exactly the message §28.6
  prescribes for those sources;
* `HEAD` changes no path outside the configured proof directory;
* `HEAD` has exactly one parent;
* amending would not leave the commit unsigned where it is currently signed —
  that is, `HEAD` carries no signature, or `ots.signing` is `required`, or
  ambient `commit.gpgsign` is set, so the replacement is signed too;
* `HEAD` is not reachable from any `refs/remotes/*` ref.

If any does not hold, the command SHALL create an ordinary upgrade commit as
§28.6 describes. The signature and reachability conditions SHALL additionally
be reported on stderr, because those are the cases in which squashing was
requested, the commit was otherwise eligible, and it did not happen.

Reachability SHALL be evaluated against the local repository's own
remote-tracking refs; the tool SHALL NOT contact a remote to decide it. This
condition SHALL be understood as detecting publication, not as establishing
its absence: a commit pushed from another clone, pushed to a URL that leaves
no tracking ref, or pushed since the last fetch is not distinguishable from an
unpublished one by any local query, and SHALL therefore be amended. The
documentation SHALL say so rather than promise that pushed commits are
protected. A local tag or another local branch pointing at `HEAD` SHALL NOT be
a decline: amending moves only the current branch and those refs keep the
previous object.

The eligibility conditions SHALL be evaluated against a single resolved object
ID. Immediately before each amendment attempt, including retries after lock
contention, the command SHALL check that `HEAD` still names that ID.
`git commit --amend` rewrites whatever `HEAD` names at the moment it runs, and
the repository lock of §24 excludes only other invocations of this tool, so a
concurrent ordinary commit can move the branch in between. If `HEAD` has
moved, the command SHALL fail with the inconsistent-repository-state exit code
rather than amend the commit that arrived; the upgraded proofs are already
written and staged, so a later invocation records them -- once the operator
has cleared the worktree, where `ots.requireCleanWorktree` is set.

This check is not atomic with Git's amendment: a concurrent writer can still
move `HEAD` between the check and Git reading it. Documentation SHALL state
that operators must avoid concurrent repository mutations while squashing.

The message condition is deliberately stricter than the trailer-only
classification of §13. The generated trailer identifies a commit as metadata;
it does not establish that this tool wrote the commit as it now stands. A
`git rebase -i` that squashes an upgrade commit into an ordinary one
concatenates the two messages, so the result carries both trailers alongside
the operator's own subject and body. Amending it would preserve its tree but
replace its message, destroying the only copy of that text. Requiring the
whole message subsumes the two trailer conditions an upgrade commit's message
always satisfies — `OpenTimestamps-Generated: true` present and
`OpenTimestamps-Source` absent — so a proof commit is likewise never a target.
A `commit-msg` hook or `commit.cleanup` setting that alters the message as it
is written makes every upgrade commit in that repository ineligible. That is a
consequence of the condition, not an exception to it: the tool SHALL NOT
loosen the comparison to accommodate it, and SHALL report the mismatch at a
diagnostic level below warning, so that a repository in which the setting can
never take effect is explicable on request without every foreign commit at
`HEAD` producing a warning.

The condition establishes shape, not provenance, and SHALL NOT be described as
proof of authorship. Git records no durable marker that this tool created a
given object, so a commit constructed by other means to be byte-identical,
touching only the proof directory, with one parent and no known publication,
is a valid target and SHALL be treated as one. The remaining conditions exist
to keep the set of commits with that shape to ones where amending loses
nothing.

Squashing SHALL be understood to discard the per-refresh chronology. The union
of `OpenTimestamps-Upgraded` trailers preserves *which* sources were
refreshed, and the proof files themselves are unaffected — a Bitcoin
attestation carries its own block, and no commit date has ever been part of
what a timestamp asserts (§9, §35). What the fold removes from reachable
history is the superseded commit objects and the committer timestamp of each
individual refresh: afterwards the repository cannot say when it obtained a
given attestation. The documentation SHALL state this, because it is the cost
an operator is accepting and it is not recoverable once the commits are
unreachable.

The amended commit's message SHALL name the union of the
`OpenTimestamps-Upgraded` trailers of the commit being amended and the sources
upgraded by this pass, in that order and without duplicates, and its subject
SHALL be the one §28.6 gives for that number of sources — a squashed commit is
indistinguishable from the single commit the same upgrades would have produced
had they arrived together, which is also what lets the next squash recognize
it. Only the proof paths this pass rewrote SHALL be updated; every other path
in the amended commit's tree SHALL be carried over unchanged, as SHALL its
author date.

`git ots upgrade --dry-run` SHALL make the same eligibility decision, without
writing anything, whenever it reports that a proof would be upgraded, and SHALL say
whether those proofs would be folded into the commit at `HEAD` or recorded in
a new commit.

The default SHALL be `false`. Amending is a history rewrite, and the
specification does not make that choice on an operator's behalf. Nothing this
tool creates depends on an upgrade commit's identity: an upgrade commit is
never a meaningful commit (§14), never carries a timestamp tag (§12), and is
never a proof-commit baseline (§17), because it makes no `OpenTimestamps-Source`
claim. A proof commit SHALL never be amended for the same reason it is
excluded above: it dates a submission and is the recovery artifact §22.3 reads
back, whereas an upgrade commit only records that a file was refreshed.

## 28.7 Configuration and proof discovery

There is no configuration file, and therefore no file to discover. Settings are
read from Git config under the `ots.*` namespace (§5), and *Git* resolves them:
scope precedence, key precedence and the parsing of every value are Git's, not
this tool's.

The tool SHALL read the whole namespace across all scopes and SHALL NOT
implement a search path of its own. Resolution is therefore Git's documented
order — `system`, then `global`, then `local`, then `worktree`, each overriding
the last — with `git -c` and the `GIT_CONFIG_*` environment variables
overriding all of them.

Repository discovery precedes configuration reading, because the repository is
what determines which `local` and `worktree` scopes exist. Invoking the tool
outside any Git repository SHALL produce the documented repository-state error.
The repository-location lookup itself runs before any configured timeout is
known and is therefore bounded by the built-in default (§5).

The namespace being empty SHALL NOT be an error: the defaults of §5 apply and
the tool SHALL proceed. A value Git rejects — an unparseable boolean, an
invalid duration — SHALL map to the invalid-configuration exit code, carrying
Git's own diagnosis. A key under `ots.*` that this specification does not
define SHALL likewise map to the invalid-configuration exit code, naming the
offending key and the namespace; a typo is a misconfiguration, not a setting to
ignore silently.

A `git-ots.toml` file left over from an earlier version SHALL be ignored
entirely: not read, not validated, not mentioned in diagnostics. It has no
meaning to this tool. Note that an untracked leftover file still makes the
worktree dirty, so under `ots.requireCleanWorktree` the run may legitimately
refuse to proceed on those ordinary grounds — that is the cleanliness
precondition of §25 acting, not the file being read.

Because Git config is never carried by a clone, a fetched repository cannot
supply configuration to this tool. That is the security property the format
exists for
and that is why no `--config` flag is offered: a path-valued flag would
reintroduce exactly
the reachable-configuration surface the design removes.

Read-only proof discovery SHALL be independent of ambient configuration.
`validate` and `verify` SHALL inspect an explicit `--proof-dir` when supplied;
otherwise the conventional `.opentimestamps/` directory when it contains
proofs; otherwise every directory containing a tracked `*.ots` file reported
by `git ls-files`. An explicit directory SHALL be repository-relative and
subject to the same containment validation as the configured write directory.
Finding no proofs SHALL be reported as “nothing was validated” or “nothing was
verified”, never as successful proof verification.

## 28.8 Configuration report

```text
git ots config
```

SHALL print the effective value of every setting of §5 together with the origin
that produced it, and SHALL take no arguments. It is read-only: it never writes
a key, and never creates configuration.

The origin SHALL be drawn from exactly this vocabulary:

```text
git config system
git config global
git config local
git config worktree
git config command
default
```

`git config command` covers `git -c` and the `GIT_CONFIG_*` environment
variables. `default` means no scope supplied the value and the built-in default
of §5 applies.

Where a key is set in more than one scope, the reported origin SHALL be the
scope that actually determined the effective value — the narrowest one — not
merely a scope in which the key happens to appear. A key whose value was set
but then discarded by the trigger-set resolution of §28.1 SHALL report
`default`, because `default` is what the run will actually use.

No other origin kind SHALL appear. In particular there SHALL be no file-path
origin and no flag origin, because no input can produce one.

# 29. Exit codes

Recommended exit codes:

```text
0   success; no timestamp required
0   success; timestamp created
1   general operational failure
2   invalid configuration
3   invalid Git repository state
4   OpenTimestamps submission, upgrade, or verification failure
5   proof persistence failure
6   Git tag/commit failure
7   repository locked by another process
```

A `git_timeout` expiry does not always surface as code 6: some internal Git
checks catch the underlying failure and relabel it as invalid Git repository
state, which surfaces as code 3 instead.

The tool additionally returns 130 when interrupted by `SIGINT`.

Normal "nothing to do" behavior is not an error.

`run` returns 0 whether it created a timestamp, completed an earlier run's
bookkeeping, or correctly did nothing, and this SHALL remain the default: a
scheduler wrapper that treats a non-zero code as a failure must not begin
reporting failures for the most common outcome. Where a caller needs the
distinction, the implementation SHALL make it available on request:

```text
100  run --exit-code: nothing was due and nothing was repaired
```

The value sits outside the range above so it can never be mistaken for a
failure the table defines. The table itself stays small; per-run detail belongs
in structured output, not in more codes.

# 30. Logging

Normal output SHOULD be concise.

Example when no action is required:

```text
No timestamp required: 2 pending commits, oldest age 7h14m.
```

Example when timestamping:

```text
Timestamping 7f31a9c4d622 (fixed_time)
Proof: .opentimestamps/7f31a9c4d622....ots
Tag: ots/20260808T220003Z/7f31a9c4d622
Proof committed.
```

Diagnostic logging SHOULD be available through:

```text
-v
```

or:

```text
--verbose
```

A global `--debug` option before the subcommand, or `GIT_OTS_DEBUG=1`, SHALL
enable verbose logging and full tracebacks for unexpected exceptions without
changing their exit codes. Without debug mode, an unexpected exception SHALL
produce one concise line naming its exception type and explaining how to rerun
with `--debug`. Debug tracebacks SHALL be emitted verbatim to local stderr; the
documentation SHALL warn that paths, branch names, and filenames may need review
before public sharing.

Logs SHALL never be used as persistent state.

# 31. Configuration validation

Startup SHALL fail before side effects if:

* a key under `ots.*` is not one this specification defines. The diagnosis
  SHALL name the offending key in Git's canonical lower-case spelling and name
  the namespace;
* a value Git rejects for its declared type — notably a boolean spelling
  outside Git's own vocabulary. The diagnosis SHALL be Git's;
* a duration is invalid or non-positive. `0` is accepted only for
  `ots.otsTimeout` and `ots.gitTimeout`, where it means unbounded (§5);
* `ots.fixedTime` has invalid syntax;
* `ots.fixedTime` is set without `ots.timezone`, or `ots.timezone` without
  `ots.fixedTime` — each is meaningless alone;
* the timezone identifier is unknown;
* `ots.sourceRef` cannot be resolved;
* `ots.tagPrefix` is not a valid Git ref prefix.

Validation SHALL apply to every value present in any scope, not only to the
values that win resolution: an invalid setting is a mistake worth reporting
even when a narrower scope happens to override it.

An empty `ots.*` namespace is **not** a validation failure — it selects the
defaults of §5. Nor is a policy failure reachable by omission: the default
`ots.maxAge` trigger applies whenever no scope names an enabling trigger, and a
trigger set to a false value enables nothing and suppresses nothing, so
"every policy disabled" is not a state configuration can express (§6, §28.1).

`ots.proofDirectory` SHALL be validated against the shape §5 requires:
repository-relative, no trailing `/`, no absolute path, no `.`/`..`/empty
segment, no leading `~`, no backslash, and every segment within
`[A-Za-z0-9._-]+`. Validation SHALL be purely lexical — it SHALL NOT consult
the filesystem, so it does not depend on which repository is current or on
whether the directory happens to exist yet.

# 32. Module architecture

The implementation SHALL keep these boundaries. They are the constraints that
survive refactoring; the current responsibilities of each module are documented
in its own docstring, which is where they stay accurate.

* **Policy logic SHALL remain pure** — no Git subprocesses, no OpenTimestamps,
  no clock reads. Everything it needs arrives as an argument, so every policy
  decision is reproducible from its inputs alone.
* **All Git access SHALL be confined to the Git module.** No other module
  spawns `git`.
* **Business rules SHALL NOT be implemented inside argument-parsing code.**
  The CLI parses arguments, maps failures to exit codes, and delegates.
* **Orchestration SHALL be separable from the CLI**, so the transaction can be
  driven and tested without a process boundary.

The operation pipeline itself is normative and specified in section 21:

```text
configuration -> repository inspection -> policy evaluation ->
timestamp submission -> proof persistence -> proof commit -> tagging
```

# 34. Scheduler expectations

`git-ots` SHALL not contain an internal scheduler.

It is designed to be called by mechanisms such as:

```text
cron
systemd timer
CI pipeline
post-push automation
external scheduler
```

For example, a 5-minute scheduler combined with:

```text
git config ots.maxAge 24h
```

provides an effective worst-case detection delay of approximately:

```text
24h + 5m
```

assuming execution succeeds.

For fixed-time policies, the scheduler should run more frequently than the
precision required around the configured wall-clock time.

For `ots.everyCommit`, the command should normally be invoked by CI or another
per-push mechanism.

Because configuration lives in Git config rather than in the repository (§5),
the scope a scheduled run reads from is a real operational concern:

* A scheduled job runs as some user. It reads that user's `global` scope and
  the repository's `local` scope — not the scope of whoever configured the tool
  interactively. Configuration written to `--global` as one user is invisible
  to a timer running as another.
* Nothing in a clone can supply configuration, so a scheduled run over a freshly
  cloned repository uses the defaults of §5 until a scope on that machine says
  otherwise. This is the intended property, not an oversight.
* `git ots config` (§28.8) run *as the scheduling user, in the target
  repository* is the way to confirm what a scheduled run will actually do,
  since it reports both the effective value and its originating scope.

# 35. Security considerations

The supported runtime matrix is Linux and macOS on Python 3.12, 3.13, and
3.14. CI SHALL exercise all six combinations. Repository locking is specified
for ordinary local filesystems and linked Git worktrees; network filesystems
with non-local advisory-lock semantics are outside the supported model.

The OpenTimestamps client compatibility check SHALL require the `stamp`,
`upgrade`, and `verify` commands. Missing capabilities are fatal when the
operation needs the client. A version other than the tested 0.7.2 baseline MAY
continue when the capability probe succeeds, but SHALL be reported as untested.
The repository SHALL exercise the pinned client and live calendars weekly and
on manual dispatch; installed copies SHALL schedule nothing and send no
telemetry.

The implementation SHALL:

* invoke subprocesses using argument arrays rather than shell interpolation;
* never construct shell commands from Git commit messages;
* validate tag names before use;
* validate paths before writing;
* prevent proof paths from escaping the repository;
* avoid staging unrelated files;
* avoid overwriting an existing proof unless explicitly performing a valid proof upgrade;
* never rewrite or delete existing timestamp tags automatically.

Commit messages, branch names, remote names, and configuration values SHALL be treated as untrusted input.

Before any OpenTimestamps submission, a mutating run SHALL resolve the Git
author/committer identity used for its annotated tags and generated commits. If
Git cannot resolve both a name and email, the run SHALL fail before submission
with instructions to configure `user.name` and `user.email`. The implementation
SHALL NOT invent an identity or write Git configuration.

## 35.1 Signing generated objects

`signing` SHALL control whether the implementation signs the objects it
authors — the timestamp tag of section 12 and the generated proof and upgrade
commits of sections 13 and 27. It SHALL default to `"inherit"`.

| Value | Behaviour |
|---|---|
| `"inherit"` | No signing flag is passed; ambient Git configuration applies unchanged |
| `"required"` | `-s` is passed to `git tag` and `-S` to `git commit` |

Under `"required"`, a signer that fails SHALL fail the operation rather than yield an
unsigned object.

The default SHALL NOT be named `off`. Under `"inherit"` an object may still be
signed — `commit.gpgsign` and `tag.gpgSign` in ambient configuration reach the
objects this tool creates — so `off` would misdescribe it. The name is reserved
for a mode that suppresses ambient configuration, which this specification does
not yet require; an implementation SHALL reject `"off"` with an error naming
the distinction rather than accept it as a synonym for the default.

The setting SHALL NOT apply to source commits. Whether a commit being
timestamped is signed is a property of how the repository is worked in, and the
implementation SHALL neither require nor produce signatures there.

The scope of what a signature adds is narrow, and SHALL be documented as such:

* It authenticates *who ran the tool*, which the Bitcoin attestation does not
  and cannot. It adds nothing to what that attestation proves.
* A forged tag or proof commit does not survive verification regardless — an
  attestation cannot be fabricated — so the signature defends against
  confusion and misattribution, not against a forged timestamp.
* It is the manifest, whose `submitted_at` and trigger fields no attestation
  covers, that a signature most meaningfully authenticates.
* A signature over a tag is not itself timestamped: a tag object is never the
  subject of a payload under section 9. Unlike a signature on a source commit,
  which is inside the commit object the payload names and is therefore anchored
  by the very act of timestamping it, a tag signature carries the ordinary
  key-revocation weakness a timestamp would otherwise remove.

# 36. Acceptance criteria

Version 1 is complete when all of the following hold:

1. A configured Git source ref can be inspected without affecting local repository content.
2. Generated proof commits are reliably distinguished from meaningful commits.
3. `every_commit` timestamps every pending meaningful commit.
4. `max_age` timestamps the latest meaningful state once the oldest pending state reaches the configured age.
5. `fixed_time` timestamps the latest meaningful state on the first eligible invocation after the configured time.
6. `max_age` and `fixed_time` do nothing when no meaningful changes exist.
7. Multiple aggregate triggers result in one timestamp.
8. Proof files and metadata are written into the repository.
9. Every successful submission creates an immutable annotated tag pointing at the corresponding source commit.
10. Proof commits are committed without staging unrelated changes.
11. A proof-only commit never generates another timestamp.
12. Repeated execution without new eligible state is idempotent.
13. OpenTimestamps or Git failures do not incorrectly mark a source state as successfully timestamped.
14. Concurrent runs cannot create duplicate submissions.
15. All core policy behavior is covered by unit tests.
16. End-to-end behavior is covered using temporary Git repositories.

## 36.1 Manual verification protocol

Claims that depend on external services or repository-host settings SHALL be
verified before publication using this protocol:

1. Confirm all six Linux/macOS and Python 3.12–3.14 CI matrix jobs pass.
2. Manually dispatch the OpenTimestamps compatibility workflow and confirm the
   pinned client exposes the required commands and can obtain a live calendar
   proof; an unreachable calendar is neutral, malformed protocol output fails.
3. Build the wheel and source distribution, install each in an empty
   environment, and verify `git ots --version`, help, and an offline dry run.
4. Confirm GitHub private vulnerability reporting, repository features, and
   `master` branch protection match the publication policy.
5. For a release tag, confirm the tagged commit has a stored proof on `master`,
   the GitHub Release and PyPI files have identical SHA-256 digests, and the
   GitHub provenance attestations verify.

# 37. Example normal configuration

A typical daily repository configuration:

```text
git config ots.maxAge 24h
git config ots.fixedTime 00:00
git config ots.timezone Europe/Berlin
git config ots.sourceRef '@{upstream}'
```

Only the settings that depart from the defaults of §5 need to be named. The
example above sets four; `ots.everyCommit`, `ots.initialHistory`,
`ots.fetchBeforeRun`, `ots.tagPrefix`, `ots.requireCleanWorktree`,
`ots.signing`, `ots.proofCommit`, `ots.squashUpgradeCommits` and
`ots.command` are all left at their defaults and are therefore absent — the configuration is the diff from the
defaults, not a transcription of them.

Scope is a real choice here, not boilerplate. `--local` (the default above)
confines the settings to one repository; `--global` applies them to every
repository the user owns, which is usually what a scheduled daily timestamping
setup actually wants. `git ots config` reports the effective value of every key
together with the scope it came from (§28.8).

With frequent scheduler execution, the expected behavior is:

```text
day 1 00:00  latest changed state timestamped

day 1 08:00  commit B
day 1 12:00  commit C
day 1 19:00  commit D

day 2 00:00  D timestamped
             proof stored
             D tagged
             proof committed

day 2 00:05  rerun
             no action
```

# 38. Core invariant

The central invariant of `git-ots` is:

> A timestamp tag always identifies an exact meaningful Git source state successfully submitted to OpenTimestamps, while repository changes generated solely to preserve OpenTimestamps evidence never themselves create new timestamp obligations.

All implementation decisions should preserve this invariant.
